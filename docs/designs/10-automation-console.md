# 自动化管理后台

后台首页为 `/admin/automation`。工具、教程、仓库仍为资源类型，复用同一套信源、加工和审核流程。

## 已接入的运营流程

1. 信源管理：创建 GitHub 仓库或 RSS 信源，编辑用途、频率、可信度、全文展示许可，启停和立即采集。现有外部推送信源也可查看、启停；推送凭据继续由现有运维入口管理。
2. 采集与加工：分页查看采集任务和加工阶段，按状态、来源筛选；展示原始资料、同轮次阶段、失败原因。页面定期刷新。
3. 待审核：跨三种类型查看新增或修改建议；逐字段接受、拒绝、改写，人工保护字段须显式解锁。查看证据和原文后，先预览当前决定的实际合并结果，再明确确认“采纳并发布”。拒绝不要求先预览。
4. 概览与费用：展示真实数量、活跃预算窗口、模型名称和调用结果。密钥、完整提示词、供应商响应不发送给页面。模型与额度上限仍由服务端配置，此版本不提供在线修改密钥与预算的入口。

## 事务与恢复决策

- 信源配置使用 edit_version 防止覆盖并发修改；配置与审计、幂等响应同事务提交。更换仓库或订阅地址时清空旧检查点，保留历史资料。
- 手动采集在信源行锁内拒绝重复活跃任务，采集记录、River 入队、审计和幂等响应在同一事务提交。暂停信源阻止新抓取，已有公开内容不受影响。
- 重试本阶段沿用冻结的 pipeline_plan、run_key、规则及模型 profile；只适用于失败或阻塞状态。活跃队列任务以及 prepared/sent/unknown 模型回执会阻止重试。
- 重新加工是独立、显式的操作：锁定资料后使用最新修订与当前模型 profile，递增 rerun_no。存在活跃任务、待核对模型调用或未处理建议时拒绝。页面明确提示可能产生新费用。
- 审核预览使用 ReviewService 的合并规则和发布服务的校验、标签解析及展示格式，不创建修订或发布记录，也不计访客事件。真正发布时仍重新校验资料、资源版本和草稿冲突。
- 所有接口复用管理员会话与 CSRF。写操作复用 WriteExecutor；预览是无写入的 POST，校验 CSRF，不创建幂等记录。采集网络仍使用已有 SSRF 防护、大小限制和超时。

## 接口与边界

新增接口见 `api/openapi.yaml` 的 automation 标签。列表每页最多 50 条，提供 has_more / next_offset，不把首屏 50 条误当全量。原文展示最多 30,000 字符并标明截断。

此版本聚焦“信源 → 加工 → 审核 → 预览 → 发布”。供应商结果不明的回执核对继续走现有带核对依据的运维流程；界面禁止一键重复发送。后续已扩展 JSON、网页、X、公众号与试抓，详见 `11-source-collectors.md`；付费渠道需要独立凭据与预算。
